## Executive Summary

Seven confirmed vulnerabilities cluster in three areas. **Consent/GDPR integrity** is the largest and most severe class: an unauthenticated attacker can plant forged first-party "granted" consent (with a forged Art. 7(1) proof row) for any victim email through the public booking form (F-008, HIGH), while the privacy-erasure engine destroys legally-held and statutorily-floored data because the person-erase cascade never consults the transitive `legal_hold` / GoBD guards the retention engine enforces (F-011, F-012, MEDIUM). **Authorization/agent-governance** flaws let a `lead:update`-only rep drive governed lifecycle transitions and evade the `person:create`/`lead:delete` scopes (F-003), and let a governed agent opt out of the approval version-skew binding on the REST path (F-006). **Auth-surface and data-egress hygiene** round it out: the login lockout path is an account-existence oracle (F-005), and the AI SecretStripper allowlist misses common secret classes, leaking secrets to the external LLM (F-004). Affected components span `compose/` (public booking, agent gate), `modules/people`, `modules/privacy`, `modules/identity`, and `modules/ai`.


## Findings


### 1. Anonymous public booking form plants first-party 'granted' consent for an attacker-supplied email — HIGH

| Field | Detail |
|-------|--------|
| **Severity** | HIGH (verifier confidence 8.0/10; 2 TP / 0 FP) |
| **Affected Component** | `backend/internal/compose/bookingconsent.go:42` |
| **Endpoint** | `POST /v1/public/booking/{public_slug}` (anonymous edge) |
| **Finding ID** | F-008 |
| **Class** | Consent forgery / GDPR integrity |

**Root Cause Analysis**

The public booking route runs as `PrincipalSystem system:public_booking`, which bypasses `auth.Require`/`auth.EnsureVisible` (`rbac.go:45-46,56-57`). The attacker-controlled request body (`req.Consent.{PurposeId,PolicyVersion,Wording}`, `scheduling_public.go:156,171`) flows into `ValidatePurpose` (`bookingconsent.go:34-38`), which accepts **any** tracked purpose — not just booking purposes. `EnsurePersonByEmail` (`person.go:359-363`) materializes a person from the attacker-supplied email. The `NeverOverrideExisting` guard (`store.go:277`) fires only when a prior decision exists (`current != ''`), so a fresh subject sails past it, and double-opt-in (`resolveDOIConfirmation`, `store.go:338`) runs only for `requires_double_opt_in=true` purposes. The sink `upsertConsentWithProof` (`store.go:359-377`) then writes `person_consent.state='granted'` plus an append-only, attacker-worded Art. 7(1) proof row; the outbound suppression gate `RequireGrantedForEmails` (`gate.go:60-61` → `activities/email.go:53`) subsequently treats the victim as opted-in.

**Exploit Scenario**

1. Attacker obtains the target tenant's public booking link (a shared public identifier).
2. Attacker POSTs a booking with `consent.purpose_id` set to a non-DOI purpose UUID (the default seed ships the non-DOI `transactional` purpose; a marketing-spam escalation requires an operator-configured non-DOI marketing purpose) and attacker-chosen `wording`/`policy_version`, for a victim email with no prior decision on that purpose. No cookie/session/Authorization is sent.
3. On `201`, a `granted` consent and an attacker-worded Art. 7(1) proof row are planted for the victim; `RequireGrantedForEmails([victim], <purpose key>)` now passes.

**Impact**

- Unauthenticated, remote forgery of first-party consent authorizing outbound sends to a victim who never opted in.
- Forged, append-only GDPR Art. 7(1) proof-of-consent records (attacker-controlled wording) — a compliance-integrity and evidentiary corruption.
- Marketing-spam escalation if the operator has configured any non-DOI marketing purpose.

**Remediation**

On the anonymous public-booking edge, constrain `ValidatePurpose` to booking-scoped purposes only — never accept an arbitrary tracked purpose from an unauthenticated caller. Require double-opt-in for any consent captured on an unauthenticated edge regardless of the purpose's `requires_double_opt_in` flag, so a fresh subject cannot be written straight to `granted`. Do not accept attacker-supplied `wording`/`policy_version` as authoritative Art. 7(1) proof from an anonymous principal; derive the proof wording server-side from the purpose's registered policy.


### 2. Lead create/update accepts terminal status values, bypassing the governed promote & disqualify flows — MEDIUM

| Field | Detail |
|-------|--------|
| **Severity** | MEDIUM (verifier confidence 9.0/10; 2 TP / 0 FP) |
| **Affected Component** | `backend/internal/modules/people/leadstatus.go:24` |
| **Endpoint** | `PATCH /v1/leads/{id}` (also the MCP/SoR twin via Bearer passport) |
| **Finding ID** | F-003 |
| **Class** | Mass-assignment / lateral authorization bypass |

**Root Cause Analysis**

The untrusted PATCH/MCP body `status` field (`handlers_lead.go:71-76`, twin `provider.go:191-196`) is mapped via a bare `string(*req.Status)` in `leadUpdateInput` (`mapping.go:229-232`) with no value filtering. The only authorization required is `auth.Require(lead, update)` (`lead_update.go:79`) — whereas the governed lifecycle handlers require the distinct `person:create` (promote) and `lead:delete` (disqualify) scopes. `ParseLeadStatus` (`leadstatus.go:24-31`) accepts all four statuses including `promoted`/`disqualified`; the OpenAPI enum `[new,working]` (`crm.yaml:8340`) is never enforced at runtime (no validator middleware; `.Valid()` is never called); and the DB CHECK (`0009_leads.up.sql:15`) permits all four. The sink `p.ApplyGuarded` (`lead_update.go:115`) commits `UPDATE lead SET status='promoted'` with audit + outbox.

**Exploit Scenario**

1. A rep holding only `lead:update`, on a lead within their own/team row-scope, sends `PATCH /v1/leads/{id}` with `{"status":"promoted"}` (`If-Match: <version>`).
2. The row is committed with `promoted_person_id`/`archived_at` NULL — no person created, no consent carried, no `lead.promoted` event. A later genuine `POST /v1/leads/{id}/promote` returns `AlreadyPromotedError` (409, empty PersonID): a permanent dead state.
3. `{"status":"disqualified"}` skips archival, breaking the `disqualified ⇒ archived` invariant. The same request works as a Bearer passport call on the MCP/SoR surface.

**Impact**

- A `lead:update`-only principal evades both the `person:create`/`lead:delete` scopes and the governed side-effects of the promote/disqualify flows.
- Corrupts the lead lifecycle: permanent dead-state leads, orphaned promotions, and a violated `disqualified ⇒ archived` invariant.

**Remediation**

Reject terminal statuses (`promoted`, `disqualified`) on the create/update path — only the governed promote/disqualify handlers (gated on `person:create`/`lead:delete`) may set them. Enforce the OpenAPI `[new,working]` enum at the transport boundary (wire a validator / call `.Valid()`), and add a workable-status guard in `ParseLeadStatus` or the store entry point so the invariant holds for both the REST and MCP/SoR surfaces. Fix all mutation sites of the `status` column as one change, not just the REST path.


### 3. Person erasure ignores the transitive legal_hold on a linked org/deal that retention enforces — MEDIUM

| Field | Detail |
|-------|--------|
| **Severity** | MEDIUM (verifier confidence 9.0/10; 2 TP / 0 FP) |
| **Affected Component** | `backend/internal/modules/privacy/erasure.go:307` |
| **Endpoint** | Automatic (nightly `RunRetention`); admin equivalent `PATCH /v1/data-subject-requests/{id}` `{"status":"fulfilled"}` |
| **Finding ID** | F-011 |
| **Class** | GDPR erasure / spoliation of legally-held data |

**Root Cause Analysis**

The `person/no_consent_no_deal` selector (`retention.go:108-115`) selects a person P on P's own attributes only, ignoring any transitive hold on a linked org/deal. `ErasePerson`'s own-hold check (`erasure.go:89-99`) passes because P itself is not held — and no transitive org/deal check exists on the erase path. `subjectOnlyActivities` (`erasure.go:307-313`) excludes an activity only when another *person* is linked; it has no org/deal `legal_hold` predicate. Retention's own transitive-hold guard (`retention.go:90-95`) — which codifies "a hold on the subject must cover the evidence about them" — is never consulted by the erase path. The sink `redactSubjectTimeline` + `eraseAttachments` (`erasure.go:323-345,168-199`) then wipes the subject/body, deletes `field_provenance`, and purges attachments that are under litigation hold.

**Exploit Scenario**

Primarily automatic (no attacker request): given an org or deal under `legal_hold`, an activity linked both to that held org/deal and to a sole person P (P has no consent and no deal stake), and an enabled `person/no_consent_no_deal` erase policy (or an admin fulfilling a DSR erasure for P), the next nightly evaluator — or the admin DSR fulfillment — destroys the litigation-held activity through the unguarded person-erase sink.

**Impact**

- Irreversible destruction of evidence the retention engine explicitly freezes (spoliation) — a legal and compliance exposure.
- A polymorphic `activity_link` makes the same activity "subject-only" to erasure yet "transitively held" to retention: a provable divergence with no gating test.

**Remediation**

Route the person-erase path through the same transitive `legal_hold` guard the retention engine uses (`retention.go:90-95`): before redacting/deleting any activity, exclude any activity transitively linked to a held org/deal. Because both engines must honor one hold predicate, extract it into a shared function and add a fitness test asserting erase and retention converge on it (per the repo's "fix the invariant, not the call site" rule).


### 4. Login account-lockout response discloses account existence (403 locked vs 401 unknown) — MEDIUM

| Field | Detail |
|-------|--------|
| **Severity** | MEDIUM (verifier confidence 8.5/10; 2 TP / 0 FP) |
| **Affected Component** | `backend/internal/modules/identity/lockout.go:116` |
| **Endpoint** | `POST /v1/auth/login` (unauthenticated) |
| **Finding ID** | F-005 |
| **Class** | User enumeration / account-takeover precursor |

**Root Cause Analysis**

For a real, active, password-set account that has been locked, `accountLockedError` is returned (`lockout.go:116-117`) **before** `password.Verify` runs, and it maps to a distinct **403 `permission_denied`** with an unscrubbed "account locked…" body (`httperr.go:115-127`) — versus **401 "invalid email or password"** for an unknown email (`handlers.go:126-128`). The decoy Argon2 timing equalizer (`service.go:144-155`) is present only on the `ErrBadCredentials` branch, not the locked branch. Unknown emails can never lock (`recordFailedLogin` ignores `ErrNoRows`, `lockout.go:150,154`), and the locked 403 never calls `Record`, so a short probe stays under the `loginPerIP` (30/min) and `loginFailures` (10/min) limiters.

**Exploit Scenario**

1. Attacker sends 5 failed logins for `target@corp.com` (each `401`; the 5th sets `locked_until = now+15m`).
2. Attacker sends one more login with any password. A real active account returns `403 permission_denied` "account locked after repeated failed logins"; an unknown/non-active email returns `401` "invalid email or password".
3. The 403-vs-401 distinction (and distinct body/timing) is a reliable account-existence oracle for the full 15-minute lockout window, evading the 429 rate limit.

**Impact**

- Confirms which employee emails have real active accounts, feeding targeted credential-stuffing and phishing.
- Incidental 15-minute lockout denial-of-service per probed account.

**Remediation**

Return an identical generic response — same status code, same body, and equalized timing (apply the decoy Argon2 pass on the locked branch too) — for the locked and unknown-account cases. Do not surface a distinct 403 or an unscrubbed "account locked" message to an unauthenticated caller before credential verification.


### 5. Approval target-version skew binding is caller-optional on the REST agent path — MEDIUM

| Field | Detail |
|-------|--------|
| **Severity** | MEDIUM (verifier confidence 8.0/10; 2 TP / 0 FP) |
| **Affected Component** | `backend/internal/compose/agentgate.go:230` |
| **Endpoint** | Mutating "yellow" REST agent calls (e.g. `DELETE /v1/deals/{id}` with `Authorization: Bearer mgp_<passport>`, redeemed with `X-Approval-Token`) |
| **Finding ID** | F-006 |
| **Class** | Logic flaw / agent-governance integrity |

**Root Cause Analysis**

When an agent omits `If-Match`, `IfMatchVersion` returns `(nil, true)` (`agentgate.go:212`, `wire.go:155-157`) — an absent header is treated as "no OCC request," not an error. `StageRequest.TargetVersion = nil` then INSERTs `target_version = NULL` (`agentgate.go:230`, `staging.go:114`) with no versioned-target guard. At redemption, `validateRedemptionTarget`'s skew check (`redeem.go:101-103`) short-circuits to nil when `TargetVersion == nil`, so it is skipped. The MCP twin (`tools_confirm.go:57-58`) and the REST field-split path (`agentsplit.go:145`) pin `&rec.Version` server-side — proving the intended invariant that this path breaks: only `stageRefusal` sources the pin from an omittable header.

**Exploit Scenario**

1. Agent stages a mutating yellow REST call without `If-Match` → `403 ErrRequiresApproval` with `target_version` stored NULL.
2. A human approves the staged request at version N (normal flow).
3. The target row drifts to N+k via any concurrent writer within the 15-minute TTL.
4. The agent redeems with `X-Approval-Token` → the skew check is skipped and the approved effect applies to the drifted row (N+k). With `If-Match: N` present it would have returned `ErrVersionSkew`.

**Impact**

- A human approves a specific version of a record, but the effect can apply to a different, drifted version — undermining the "transport never changes what a human decision protects" guarantee for governed agents.

**Remediation**

On the REST agent staging path, pin `target_version` server-side from the current record version (as the MCP twin and REST field-split already do), rather than from the omittable `If-Match` header. Treat a versionable target staged with no version pin as an error, not a skipped check; permit a NULL `target_version` only for genuinely un-pinnable entity types.


### 6. SecretStripper allowlist misses common secret classes (Stripe/AWS/URL creds) → egress to the LLM — MEDIUM

| Field | Detail |
|-------|--------|
| **Severity** | MEDIUM (verifier confidence 7.5/10; 2 TP / 0 FP) |
| **Affected Component** | `backend/internal/modules/ai/stripper.go:43` |
| **Endpoint** | N/A — outbound data egress to the external BYOK LLM (and at-rest `ai_call_payload` when `ai.capture_payloads` is enabled) |
| **Finding ID** | F-004 |
| **Class** | Secret / PII egress |

**Root Cause Analysis**

Untrusted CRM content (a note, deal description, or captured email body) carrying a secret propagates through `model.Request` → `wireMessages` → marshal (`outbound.go:99-119`; capture path `payloadcapture.go:49-52`). `SecretStripper.Strip`'s `stripRules` (`stripper.go:37-56,62`) then pass the secret verbatim: the Stripe rule `\bsk-…` is hyphen-only (misses `sk_`/`rk_` underscore keys), the AWS rule catches only the access-key **ID** (not the secret key), there is no `access_key` keyword rule, and there is no `://user:pass@` URL-credential rule. The secret egresses to the external LLM (`outbound.go:126,130`) and, with capture on, persists unredacted in `ai_call_payload` (`payloadcapture.go:71`). The authors' own test only catches `sk_live_` via an `api_key:` prefix — a bare Stripe key survives.

**Exploit Scenario**

Data-egress, not a request/response exploit: place a bare secret in a note/deal/captured email — e.g. `sk_live_51H8xN2eZvKYlo2C…`, `postgres://svc:S3cr3tPass@db.internal:5432/prod`, or `aws_secret_access_key=wJalrXUtnFEMI/K7MDENG/bPxRfiCYEXAMPLEKEY` — then trigger any AI lane over that record. `Strip()` leaves the tokens verbatim (expected-but-missing: `[SECRET-REMOVED:api_key]`); they reach the external LLM and land unredacted in `ai_call_payload` when capture is enabled.

**Impact**

- Third-party secrets and credentials in CRM/captured content egress to an external LLM — the stripper is the sole hygiene pass on both the egress and at-rest paths.
- With `ai.capture_payloads` enabled, verbatim at-rest persistence of those secrets.

**Remediation**

Broaden `stripRules` to cover underscore-form Stripe keys (`sk_`/`rk_`/`pk_`, live and test), AWS secret access keys (40-char values and the `secret_access_key`/`access_key` keywords), and URL-embedded credentials (`://user:pass@`). Prefer a defense-in-depth approach (known-prefix + high-entropy token detection) over a hand-maintained allowlist, and add regression tests using **bare, unprefixed** secrets of each class.


### 7. Person-erase cascade destroys commercial correspondence below the GoBD statutory floor — MEDIUM

| Field | Detail |
|-------|--------|
| **Severity** | MEDIUM (verifier confidence 7.5/10; 2 TP / 0 FP) |
| **Affected Component** | `backend/internal/modules/privacy/erasure.go:323` |
| **Endpoint** | Automatic (nightly `RunRetention`) in a DE workspace |
| **Finding ID** | F-012 |
| **Class** | GDPR erasure vs. GoBD statutory retention floor |

**Root Cause Analysis**

In a DE workspace, the `person/no_consent_no_deal` selector carries no floor argument because its `ObjectType` is not `activity` (`retention.go:108-115,186-192`). `apply()` routes person+erase to `ErasePerson` before the floor logic (`retention.go:268-270`), so `commercialCorrespondenceFloor` (`retention.go:74`) — applied only to the direct activity selectors — is absent on this path (`erasure.go` has no `jurisdiction` import). The sink `redactSubjectTimeline` (`erasure.go:323-328`) then runs `UPDATE activity SET subject='Erased Subject', body=NULL, archived_at=…` over the unfloored subject-only set, destroying a `<6`-year `Handelsbrief`.

**Exploit Scenario**

Automatic, gated on a non-default config: (1) the DE jurisdiction pack is compiled in and an operator has switched the seeded `person/no_consent_no_deal` policy action from the default `anonymize` to **`erase`**; (2) a person P with no granted consent and no deal stake is linked alone to a `kind='email'` activity `occurred_at` ~400 days ago (inside the 2190-day floor); (3) the next nightly `RunRetention` tick nulls the email body/subject with no floor consultation. The direct `activity/erase` policy would leave the identical email intact (per `TestStatutoryFloorShieldsCorrespondenceFromDestruction`).

**Impact**

- Destruction of commercial correspondence (Handelsbriefe) below the 6-year GoBD statutory retention floor, contradicting the DE pack invariant "a workspace policy may keep longer, never destroy earlier" (`de/pack.go:24-25`).

**Remediation**

Route the person-erase cascade through the same `commercialCorrespondenceFloor` consultation as the direct activity selectors (import the `jurisdiction` pack into the erase path). A person-erase must never destroy an activity younger than the applicable statutory floor — shield/anonymize it instead. Add a fitness test for the person-cascade path mirroring `TestStatutoryFloorShieldsCorrespondenceFromDestruction`. (The `anonymize` default is the key likelihood-limiter; the fix hardens the non-default `erase` action.)
